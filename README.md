# K-IFRS 1115 수익인식 학습 도우미

K-IFRS 제1115호 '고객과의 계약에서 생기는 수익'을 공부하다 궁금한 개념이 생기면, 그 답이 기준서 **어느 문단에 있는지** 찾아 주는 챗봇입니다.

- 질문하면 짧게 요약하고, 근거가 된 기준서 문단을 원문 링크와 함께 보여 줍니다.
- 공부를 돕는 도구라 실제 계약의 회계처리는 판단하지 않습니다.
- 서버 없이 브라우저와 내 PC의 Ollama(`qwen3.5:2b`)만으로 동작합니다.

배포 주소: https://rubilisa08.github.io/finance-rag-chatbot/ (GitHub Pages 설정 전이라 아직 열리지 않습니다. 지금은 [로컬에서 실행하기](#로컬에서-실행하기)로 써 주세요) · 제품 요구사항: [PRD.md](PRD.md)
[모두콘 안내 챗봇](https://github.com/suncreation/moducon-chatbot)의 구조를 바탕으로 만들었습니다.

## K-IFRS 제1115호란?

회사가 물건이나 서비스를 팔았을 때 **매출(수익)을 언제, 얼마로 장부에 적을지** 정한 회계 기준입니다. 정식 이름은 '고객과의 계약에서 생기는 수익'입니다.

핵심 원칙은 "돈을 받은 때"가 아니라 **"고객에게 약속한 것을 넘겨준 때"**, 그 대가로 받을 것으로 기대하는 금액만큼 수익을 인식한다는 것입니다(문단 2).

이 원칙은 다섯 단계로 적용합니다.

| 단계 | 하는 일 |
|---|---|
| 1. 계약 식별 | 고객과 계약이 실제로 성립했는지 확인한다 |
| 2. 수행의무 식별 | 고객에게 해 주기로 한 약속을 하나하나 나눈다 |
| 3. 거래가격 산정 | 받을 대가가 얼마인지 정한다 |
| 4. 거래가격 배분 | 약속이 여러 개면 가격을 약속마다 나눠 붙인다 |
| 5. 수익 인식 | 약속을 지킬 때(또는 지켜 가는 만큼) 수익으로 적는다 |

## 다루는 질문과 다루지 않는 질문

| 다루는 것 | 다루지 않는 것 |
|---|---|
| 제1115호의 핵심 원칙 | 주가 전망, 세무(절세·신고), 투자 자문 |
| 수익인식 5단계 (계약 식별 → 수행의무 식별 → 거래가격 산정 → 배분 → 수행의무 이행) | 리스, 금융상품 등 다른 기준서 |
| 계약자산·계약부채 용어, 계약변경, 진행률, 변동대가 제약, 유의적인 금융요소, 할인액 배분, 계약원가, 반품권, 보증, 본인 대 대리인, 교육용 사내 검토 절차 | 개별 계약의 회계처리 **판단과 결론** (관련 기준 문단만 안내하고 전문가 확인을 권함) |
| | 실무 판례·금융감독원 질의회신 (자료에 없음) |

자료에 없는 질문에는 "제가 가진 자료에는 없습니다"라고 답하도록 했습니다. 다만 2B 모델이라 완벽하지 않아서, 실제로 지어낸 사례도 실험 결과에 그대로 적었습니다. 상황별 처리 기준은 [PRD.md 5장](PRD.md#5-답변-규칙)에 있습니다.

**화면에서 보이는 것**: 답변 바로 아래에 **답변이 인용한 기준서 문단**(문단 번호, 원문 링크)이 펼쳐져 나옵니다. 요약보다 원문이 정확하니 링크를 열어 원문으로 확인하세요. 답변이 근거 ID를 빠뜨리면 검색 상위 문단을 "관련될 수 있는 문단"으로 보여 주고, 범위 밖 질문을 거절했을 때는 보여 주지 않습니다. 그 아래에는 프로그램이 자동으로 만든 안내 문구가 붙습니다.

> 본 답변은 K-IFRS 제1115호 기준서 요약(문단 B20~B21)에 기초한 학습용 참고 자료입니다. 저작권 때문에 기준서 원문 대신 직접 쓴 요약을 쓰므로 정확한 표현은 원문 링크에서 확인하고, 실제 회계처리는 작성자와 감사인의 판단이 필요합니다.

문단 번호는 답변이 인용한 근거에서 프로그램이 뽑아 넣습니다. 모델에게 맡기면 빠뜨리거나 틀린 번호를 쓸 수 있어서입니다.

## 기준서 원문을 그대로 쓰지 않은 이유 (저작권)

**짧게 말하면**: 기준서 문장은 저작권이 있는 글이고 이 레포는 누구나 볼 수 있는 공개 레포라서, 원문을 옮기지 않고 **직접 요약해서** 썼습니다. 원문은 복사해 두는 대신 **공식 사이트의 해당 문단으로 안내**합니다.

**1. 기준서는 누구의 글인가**
K-IFRS는 국제회계기준(IFRS)을 한국어로 옮긴 것이고, 원 저작권은 **IFRS 재단**에 있습니다. 한국회계기준원 회계기준열람서비스의 [저작권 고지](https://db.kasb.or.kr/s/1115/copyright)에는 재단의 서면 승인 없이 기준서의 전부나 일부를 번역·복제·재배포하는 것을 원칙적으로 금지한다는 내용이 있습니다. 한국 안에서 쓰는 경우에 대해 일부 권리를 주장하지 않는다는 예외 문구도 있지만, 전 세계에 공개되는 GitHub 레포가 그 예외에 들어가는지는 분명하지 않습니다.

**2. RAG에서는 왜 특히 문제가 되나**
RAG 챗봇은 자료를 청크 파일(`data/chunks.json`, `app/public/ifrs-docs.json`)에 담아 레포에 올리고, 배포한 페이지가 방문자의 브라우저로 이 파일을 내려보냅니다. 청크에 원문을 그대로 넣으면 **기준서 일부를 레포와 배포 페이지를 통해 그대로 다시 배포하는 셈**이 됩니다.

**3. 그래서 이렇게 했습니다**
- 청크의 `text`는 해당 문단을 **내 말로 요약**했습니다. 수행의무, 개별 판매가격처럼 뜻이 정해진 회계 용어는 정확성을 위해 그대로 썼습니다.
- 요약과 원문이 얼마나 겹치는지 프로그램으로 쟀습니다. 가장 길게 겹치는 구간이 청크마다 **11~33자**(용어나 짧은 구절 수준)이고, 문장을 통째로 옮긴 곳은 없습니다.
- 모든 기준서 청크에 **문단 번호**와 열람서비스의 **해당 목차 URL**을 붙였습니다. 원문을 레포에 복사하는 대신 공식 사이트의 원문을 읽도록 안내하는 방식입니다.
- 요약을 검증하려고 모은 원문 발췌본은 **레포 밖의 내 PC에만** 두었고, 레포에는 올리지 않았습니다.
- 화면의 답변 아래 안내 문구와 이 README에 이 사실을 적었습니다.

**4. 쓰는 사람이 알아 둘 점**
- 답변은 "기준서를 요약한 자료"를 다시 요약한 것이라, **표현이 원문과 다를 수 있고 요약 과정의 오류가 있을 수 있습니다.** 공부할 때는 근거 문단의 원문 링크를 꼭 열어 보세요.
- 과제, 시험 답안, 실무 문서에 인용할 때는 이 챗봇의 문장이 아니라 **원문 문장**을 쓰세요.

**5. 이 방식의 대가**
원문을 그대로 넣었다면 표현은 더 정확했을 것입니다. 요약하면서 원문에 없는 해석이 섞일 위험이 생기는데, 이것은 원문과 한 문장씩 대조하는 검토로 관리했습니다. 이 판단은 법률 자문을 받은 것이 아니라 공개 레포에서 가장 무난한 방식을 고른 것입니다.

## 사용 조건

실행하기 전에 확인해 주세요.

1. **Ollama 실행**: [Ollama](https://ollama.com)를 설치하고 모델을 받습니다.
   ```bash
   ollama pull qwen3.5:2b
   ```
2. **첫 방문 시 임베딩 모델 다운로드**: 첫 질문 때 embeddinggemma-300m(약 200MB)을 한 번 받고, 이후에는 브라우저 캐시를 씁니다.
3. **CORS 설정 (배포 주소에서 쓸 때)**: GitHub Pages 주소에서 로컬 Ollama를 부르려면 `OLLAMA_ORIGINS`에 `https://*.github.io`를 허용하고 Ollama를 다시 시작해야 합니다.
   - Windows: 작업 표시줄에서 Ollama 종료 → `계정의 환경 변수 편집`에서 새 변수 `OLLAMA_ORIGINS` = `https://*.github.io` → Ollama 다시 실행
   - macOS: `launchctl setenv OLLAMA_ORIGINS "https://*.github.io"` 후 Ollama 재시작
4. **브라우저**: Chrome 또는 Edge를 권장합니다. "로컬 네트워크 접근"을 물으면 허용합니다.
5. **속도**: GPU가 없으면 답변에 1~3분, 판정(LLM-as-a-Judge)에 몇 분이 더 걸릴 수 있습니다.

### 실행 순서
① 배포 주소를 열고 이 챗봇이 다루는 자료와 질문을 읽습니다. ② 내 PC에서 Ollama를 실행하고 `qwen3.5:2b`를 준비합니다. ③ 첫 질문 때 임베딩 모델 다운로드를 기다립니다. ④ `OLLAMA_ORIGINS`를 설정한 뒤, 안내한 질문(예: "계약부채가 뭐야?")과 자료 밖 질문(예: "내일 삼성전자 주가 오를까요?")을 각각 입력해 봅니다.

### 로컬에서 실행하기
```bash
cd app
npm install
npm run dev
```
`http://localhost:5173`에서는 CORS 설정 없이 동작합니다.

## 설계 결정 요약

- **"안내 챗봇"이 아니라 "학습·문단 찾기 도우미"**: 처음에는 회계팀 실무자에게 기준을 안내하는 챗봇으로 시작했지만, 실험에서 가장 크게 틀린 것이 실제 계약 판단 질문과 자료에 없는 주제 질문이었습니다. 2B 모델과 요약 자료로 실무 판단을 돕는 것은 위험하다고 보고, 사용자를 학습자로 좁혔습니다(PRD v2.0). 시스템 메시지만 바꾸는 방법은 효과가 없어서(실험 5 기각), 근거 문단을 답변 아래에 펼쳐 보여 주고 면책 문구를 프로그램이 붙이는 방식으로 구현했습니다.
- **도메인을 제1115호 하나로 좁힘**: 회계기준 전체를 다루면 청크 몇 개로는 근거가 부족해집니다. 범위를 좁혀 "자료 안 / 자료 밖"의 경계를 분명히 했습니다.
- **원문 출처와 문단 번호**: 모든 청크는 한국회계기준원 회계기준열람서비스의 해당 목차 페이지 URL과 기준서 문단 번호를 가집니다. 출처 칩 → "기준서 원문 보기"로 원문의 해당 위치를 찾을 수 있습니다.
- **청크는 직접 요약**: 공개 레포에 기준서 문장을 옮기지 않기 위해 `text`는 문단을 직접 요약했습니다. 원문에 없는 해석·예시·수치는 넣지 않았습니다.
- **사례 판단 질문은 거절하지 않음**: 신입이 실제로 많이 물을 질문이라, 결론은 내리지 않되 판단에 필요한 기준은 근거와 함께 안내합니다.
- **임베딩 공간 통일**: 질문 임베딩(`app/src/rag.ts`의 `embed()`)과 같은 모델 파일·같은 계산으로 청크 벡터를 만들었습니다(`app/scripts/embed-docs.mjs`). 같은 문장을 Node와 브라우저에서 임베딩해 결과가 일치하는 것을 확인했습니다.
- **임베딩 계약을 한 곳에서 정의**: 모델과 입력 형식(문서 `title: 섹션 | text: 본문`, 질문 `task: search result | query: 질문`)은 `app/src/embed-format.ts`에만 있고 브라우저와 Node가 함께 씁니다. 벡터스토어 옆 `ifrs-docs.meta.json`의 설정이 현재 설정과 다르면 검색을 거부합니다. 입력 형식은 아래 실험 1의 측정값으로 정했습니다.
- **바꾸지 않은 것과 바꾼 것**: 검색 순서, 근거 원칙, 판정 로직은 모두콘 구조 그대로입니다. 임베딩 입력 형식과 출처 표시 형식은 실험으로 근거를 남기고 바꿨습니다. 아래 [과제 조건과 달라진 점](#과제-조건과-달라진-점) 참고.
- **근거 표시는 프로그램이 확인**: 2B 모델은 ID를 빼먹거나 다르게 적기도 하므로, 출처 칩의 ✓(답변에 ID가 실제로 적힌 근거)는 모델이 아니라 프로그램이 답변을 보고 붙입니다.

### 실험 1 — 임베딩 입력 형식

### 생각해 볼 것
1. **단어가 겹치지 않아도 찾을 수 있나?** 임베딩은 단어가 아니라 뜻을 비교하므로 가능은 합니다. 2번에서 정답이 "계약부채"라는 단어 없이도 3위 안에 들었습니다. 하지만 우리 자료에서는 **1위까지는 못 올라왔고**, 5번 "선수금"처럼 실무 용어와 기준서 용어가 다르면 거의 못 찾았습니다(17위). 실무 용어(선수금)와 기준서 용어(계약부채)를 잇는 문장이 청크에 있으면 나아질 수 있습니다.
2. **8·9번도 1위 청크는 항상 나옵니다.** 검색은 "가장 가까운 것"을 고를 뿐 "답이 있는지"는 모릅니다. 그래서 점수 기준(0.55)이 필요하고, 실제로 무관한 질문(0.42~0.49)은 걸러졌습니다.
3. **7·10·11번은 기준을 통과해 버립니다.** "매출", "회계처리", "법인세"처럼 회계와 가까운 단어가 있으면 점수가 올라갑니다. **검색 점수만으로는 "실시간 매출은 자료에 없다", "리스는 범위 밖이다"를 걸러 낼 수 없습니다.** 그래서 시스템 프롬프트에 범위 밖 규칙(주가·세무 거절, 다른 기준서 안내)을 넣었습니다.
4. **단어 하나에 끌려 엉뚱한 청크가 올라오기도 합니다.** 10번은 "회계처리"에 사내 가이드가, 7번은 "매출"에 변동대가 청크가 끌려왔습니다. 그래서 모델에게 "근거에 있는 내용만" 쓰라고 해야 합니다.

→ 이것이 "검색만으로는 부족하고 생성 단계(규칙을 아는 LLM)가 필요한 이유"입니다.

### 내가 쓴 문서 추가 전후 비교 (사내 가이드 3개)
같은 질문을 사내 가이드 청크 3개(IFRS-015~017)를 빼고(14개) / 넣고(17개) 검색했습니다.

| 질문 | 추가 전 1위 | 추가 후 1위 |
|---|---|---|
| 판단이 안 서는 계약은 누구한테 물어봐? | IFRS-003 계약의 정의 **0.670** (엉뚱함) | **IFRS-016 판단이 어려운 계약 처리 0.720** |
| 검수 확인서는 어디에 보관해? | IFRS-003 계약의 정의 **0.553** (엉뚱함, 기준을 겨우 넘음) | **IFRS-017 증빙과 기록 보관 0.696** |
| 계약서 받으면 회계팀은 뭘 확인해? | IFRS-002 계약 식별 기준 0.672 (비슷하지만 다른 내용) | **IFRS-015 계약 검토 체크리스트 0.766** |
| 계약부채가 뭐야? | IFRS-014 0.772 | IFRS-014 0.772 (그대로). 단, **3위가 IFRS-004 → IFRS-015로 바뀜** |
| 수행의무는 어떻게 식별해? | IFRS-004 0.703 | 그대로 (1~3위 모두 같음) |

1. **추가 전에도 ⚠ 경고가 뜨지 않았습니다.** 점수는 0.553~0.672로 기준을 넘었지만 내용은 엉뚱했습니다. 특히 "계약서 받으면 회계팀은 뭘 확인해?"에 기준서의 계약 식별 기준이 나온 것은 **비슷해 보이지만 다른 상황**입니다(사내 절차 질문인데 회계기준이 답으로 쓰일 수 있음). 점수 기준만으로는 맞는 자료인지 보장할 수 없습니다.
2. 자료를 넣자 **정확한 청크가 높은 점수로 1위**가 됐습니다. RAG의 답변 품질은 **자료가 있느냐**에 가장 크게 좌우됩니다.
3. 상관없어 보이는 "계약부채" 질문도 **3위가 바뀌었습니다.** 자료를 바꿀 때마다 이 관찰 질문들을 다시 돌려 봐야 합니다.

### 실험 2 — 사내 가이드에 "실무 용어와 기준서 용어" 절 추가
- 바꾼 변수: 자료 하나 — `docs/revenue-guide.md`에 `## 실무 용어와 기준서 용어` 절을 추가해 청크 IFRS-018로 넣음 (17 → 18청크). 임베딩·검색·프롬프트는 그대로.
- 이유: 위 관찰 5번에서 "선수금"처럼 실무 용어로 물으면 기준서 용어(계약부채) 청크를 거의 못 찾았습니다(17위). 기준서 청크에 "선수금"을 넣으면 원문에 없는 내용이 되므로, **사내 관행**(이 실무 용어는 이 기준으로 검토한다)으로 가이드에 적었습니다.

| 질문 | 추가 전 1위 | 추가 후 1위 | IFRS-018 순위 |
|---|---|---|---|
| 선수금은 어떻게 처리해? | IFRS-009 거래가격 배분 0.584 (엉뚱함) | **IFRS-018 0.612** | 1위 |
| 매출할인이나 리베이트는 어떻게 반영해? | IFRS-007 변동대가가 생기는 경우 0.687 | **IFRS-018 0.709** (2위 IFRS-007) | 1위 |
| 미청구 금액은 뭐로 봐야 해? | IFRS-006 거래가격 산정 0.640 (엉뚱함) | IFRS-006 0.640 그대로 | **2위** (0.620) |
| 세트로 묶어서 팔면 수행의무는 어떻게 봐? | IFRS-004 수행의무 식별 0.629 | 그대로 | 5위 |

회귀 확인 (원래 질문 10개의 1위):
- 정상 질문 5개(계약부채, 변동대가, 수행의무, 판단 보류, 검수 확인서)는 1위와 점수가 **모두 그대로**였습니다.
- 무관 질문(날씨, 김치찌개)도 그대로 ⚠ 표시됩니다.
- **부작용 1건**: "우리 회사 이번 달 매출이 얼마야?"(도메인 밖)의 1위가 IFRS-008(0.613) → IFRS-018(0.617)로 바뀌었습니다. 새 절의 "매출"이라는 단어에 끌린 것입니다. 원래도 기준(0.55) 위였어서 걸러지지 않는 것은 같고, 거절은 프롬프트 규칙에 맡깁니다.

- 결정: **채택.** 실무 용어 질문 2개에서 용어 대응 청크가 1위, 1개에서 2위로 올라왔고 정상 질문은 나빠지지 않았습니다.
- 한계: 용어 대응 청크는 "어느 기준으로 검토하라"까지만 알려 줍니다. 정의(계약부채 IFRS-014)는 여전히 상위 3위 밖이라, 모델이 두 청크를 이어 답해야 합니다. 앱은 근거를 15개 넘기므로(18개 중) IFRS-014도 모델에 전달되기는 합니다.
- 관찰: 청크가 18개인데 앱은 근거를 15개 넘기므로, 지금 규모에서는 **검색이 "무엇을 빼느냐"보다 "어떤 순서로 보여 주느냐"**에 가깝습니다. 자료가 늘면 이 차이가 커집니다.

### 실험 3 — 출처 표시 형식 (프롬프트)
- 바꾼 변수: 프롬프트의 출처 표시 형식 하나 (자료 줄 모양 + 출처 규칙 문장). 검색·자료(18청크)·질문·순서는 그대로.
- 먼저 바꾼 설정: 답변 호출에 `temperature: 0`을 넣었습니다(전에는 판정에만 있었음). 같은 질문에 같은 답이 나와야 형식 차이를 비교할 수 있기 때문입니다. 세 형식 모두 이 조건에서 돌렸습니다.
- 질문 5개 (`data/exp3-questions.json`), 근거 15개, qwen3.5:2b. 원문 답변: `experiments/exp3-v1.json`, `exp3-v2.json`, `exp3-v3.json`
- 측정은 프로그램이 합니다(`app/scripts/run-questions.mjs`): 넘긴 근거의 ID가 답에 있나(cited), 자료 줄 머리 `[IFRS-xxx | 섹션]`을 베꼈나, 넘기지 않은 ID를 지어냈나

| 형식 | 자료 줄 | 출처 규칙 | cited | 머리 베낌 | 가짜 ID | 평균 |
|---|---|---|---|---|---|---|
| v1 (모두콘 그대로) | `[IFRS-016 \| 섹션] 본문` | "근거가 된 조각의 [ID]를 답 안에서 표시" | 4/5 | **3/5** | 0/5 | 191초 |
| v2 (튜토리얼 STEP 6) | `[IFRS-016] (섹션) 본문` | "ID만 **[IFRS-014]**처럼 … 문장 끝에" + 질문 뒤에 한 번 더 | 2/5 | 0/5 | **1/5** | 183초 |
| **v3 (채택)** | `[IFRS-016] (섹션) 본문` | v2와 같되 예시 ID = **이번 질문의 검색 1위** | 3/5 | **0/5** | **0/5** | 155초 |

관찰:
- **v1**: 튜토리얼이 경고한 대로 자료 줄 머리를 통째로 베꼈습니다(`(IFRS-016 | 교육용 사내 가이드 - 판단이 어려운 계약 처리)`). 또 "계약부채가 뭐야?"에 정답 청크가 1위인데도 **"자료에 명시되어 있지 않습니다"라고 잘못 거절**했습니다.
- **v2**: 머리 베낌은 사라졌지만, 출처 예시의 ID까지 베껴 "수익인식 5단계가 뭐야?"에 **넘기지도 않은 `[IFRS-014]`를 인용**했습니다. 존재하지 않는 근거라 가장 위험한 실패입니다.
- **v3**: 예시 ID를 검색 1위 청크로 바꾸자 가짜 ID가 없어졌고, 계약부채 질문도 정확히 답했습니다.
- 공통 남은 문제: v2·v3이 놓친 인용은 모두 ID 대신 **"(문단 53)", "(부록 A 용어의 정의)"**처럼 문단 번호로 출처를 달았습니다. 청크 본문 끝의 문단 표기를 따라 한 것으로 보입니다(다음 실험 후보).
- v1의 cited 4/5 중 3개는 머리를 베낀 인용이라, 개수만 보면 v1이 높지만 품질은 v3이 낫습니다.
- 결정: **v3 채택** (`app/src/prompt.ts`의 `PROMPT_FORMAT = "v3"`). v1·v2도 비교 재현을 위해 코드에 남겨 둡니다.

- 정상 질문 ID 인용 **8/11** (그중 1건은 엉뚱한 청크 인용), 머리 베낌 0, 넘기지 않은 ID 지어냄 0.
- 평균 생성 시간 180초 (CPU, 처음 14개 179초 · 추가 4개 185초).

**심각한 실패 2건**
1. **근거 부족 질문에서 환각**: 라이선싱은 일부러 넣지 않은 주제인데, 모델이 "라이선스 기간에 걸쳐 수익을 인식해야 한다"고 지어내고 관계없는 문단 번호를 붙였습니다. 검색 1위(0.666)가 기준 위라 약한 근거 경고도 없었습니다. "1115호 안의 주제지만 자료에 없는" 질문이 가장 위험합니다.
2. **사례 판단 질문에서 검색 실패 + 결론**: "수행의무가 몇 개야?"에 검색 1위가 계약원가(IFRS-026)였고, 모델이 그걸 근거로 "1개"라고 결론을 냈습니다. 정답에 필요한 IFRS-005(구별되는 재화나 용역)는 1위가 아니었습니다.

**추가 4개에서 본 것**
- **일상어 질문에 검색이 약합니다.** "대금을 먼저 받으면", "매출"은 청크에 없는 말이라, 계약부채 정의(IFRS-014, "이미 대가를 받았거나")가 근거 15개에 들지 못했습니다. 사내 가이드의 용어 대응 절(IFRS-018 "선수금은 계약부채에 해당하는지 검토")이 1위로 잡혀 결론은 맞혔지만, 모델은 그 아래의 금융요소 청크로 이유를 댔습니다.
- 기준서 용어로 물으면("기간에 걸쳐… 조건", "계약부채") 정답 청크가 1위로 잡히고 답도 정확합니다.
- 두 개념을 비교하는 질문은 한 청크 안의 비교(계약자산 vs 계약부채)로 바뀌었습니다. 여러 청크를 잇지 못하는 문제("5단계" 질문)와 같은 원인으로 봅니다.

**그 밖의 관찰**
- 출처를 ID 대신 문단 번호로 다는 문제(실험 3)가 계속되고, 사내 가이드 답변에는 없는 문단 번호("문단 2")를 지어냈습니다.
- "5단계가 뭐야?"처럼 여러 청크를 이어야 하는 질문은 검색은 다섯 단계를 모두 넘기지만(실험 1·관찰 실습) 2B 모델이 한 청크만 씁니다.

**다음 실험 후보** (한 번에 하나씩)
- 청크 본문 끝의 "(문단 N)" 표기를 빼고 `section`에만 두기 → 문단 표기 인용·지어낸 문단 번호가 줄어드는지
- 근거 부족 질문 대응: 프롬프트에 "질문의 핵심 용어가 자료에 없으면 없다고 답한다" 규칙 추가 → 라이선스 질문 거절 여부
- 사례 판단 질문: "수행의무 몇 개" 같은 표현이 IFRS-004·005를 찾도록 사내 가이드 용어 대응 절에 연결 문장 추가
- 일상어 질문: 사내 가이드에 선수금 처리 절을 추가 → "대금을 먼저 받으면…"이 IFRS-014를 근거 안에 넣는지

### 실험 5 — 시스템 메시지를 "학습·문단 찾기 도우미"로 (v3 → v4)

## 왜 K-IFRS 제1115호인가

이 도메인을 고른 이유는 세 가지입니다. 이유마다 실제 측정 결과와 한계를 함께 적습니다.

**1. 5단계 모형이라는 분명한 구조**
- 기대: 기준서가 "계약 식별 → 수행의무 식별 → 거래가격 산정 → 배분 → 인식"으로 짜여 있어, 청크를 단계별로 나누고 질문이 몇 단계에 해당하는지 찾기 쉽다.
- 결과: 청크 `section`을 `수익인식 5단계 - 3단계 거래가격 산정 (문단 47)`처럼 단계와 문단으로 구조화했고, **검색은 이 구조대로 동작**했습니다. 단계별 직접 질문은 정답 청크가 1위였고(실험 1·4: 직접 질문 7/7, 새 주제 질문 10/12), "5단계가 뭐야?"에는 1~5단계 청크가 모두 상위 10위 안에 들었습니다.
- 한계: **답변 단계에서는 구조가 다 살지 못했습니다.** 2B 모델이 여러 청크를 잇지 못해 "5단계" 질문에 한 단계만 답했고, 근거 부족 질문에서 환각이 1건 나왔습니다(고정 질문 실험). 구조 덕분에 검색은 정확하지만, 환각이 적다고 말하기에는 아직 근거가 부족합니다. 또 기준서 본문에는 5단계를 한곳에 나열한 문단이 없어서 개요 청크를 기준서 문단으로 만들 수 없었습니다.

**2. 도메인 밖 질문의 경계가 분명함**
- 기대: 1115호는 "수익을 언제, 얼마로 인식하는가"만 다루므로 주가·투자·세무 질문을 깔끔하게 거절할 수 있다.
- 결과: 시스템 메시지에 "본 챗봇은 K-IFRS 제1115호 회계기준 범위 내의 질문에만 답변할 수 있습니다"를 정해 두었고, 고정 질문 실험에서 **도메인 밖 질문 5개(주가, 주식 매수, 법인세, 개인 세무, 이번 달 매출)를 모두 거절**했습니다. 주가·주식 질문은 정해진 문구 한 줄로 답했습니다. 동시에 **정상 질문 7개는 하나도 잘못 거절하지 않았습니다.**
- 한계: 검색 점수만으로는 경계가 갈리지 않습니다. "법인세", "매출", "리스"처럼 회계 단어가 섞인 질문은 점수가 0.58~0.63으로 기준(0.55)을 넘어서, 거절은 모델이 규칙을 지키는 데 달려 있습니다. 그리고 가장 어려운 건 도메인 밖이 아니라 **"1115호 안이지만 자료에 없는" 질문**이었습니다(라이선스 질문에서 환각).

**3. 공식 원문이 있어 근거를 확인할 수 있음**
- 기대: 기준서는 공식 원문과 문단 번호가 있어 "기준서 조항을 근거로 답한다"고 설명하기 좋다.
- 결과: 모든 기준서 청크는 한국회계기준원 회계기준열람서비스의 실제로 열리는 URL과 문단 번호를 가지고, 출처 칩 → "기준서 원문 보기"로 해당 위치를 찾을 수 있습니다. 청크는 원문과 대조해 만들었고(가장 긴 겹침 11~33자), 저작권 고지를 화면과 README에 넣었습니다.
- 한계: 공개 레포라 원문 대신 **직접 쓴 요약**이어서, 요약의 정확성은 사람이 원문과 대조해 확인해야 합니다. 사내 가이드 청크 4개는 교육용 가상 문서라 "기준서 조항"이 아니라 사내 절차 근거로 구분해 읽어야 합니다. 처음 정한 불편(비용 처리 기준)과 달리 도메인은 수익인식이라, 사용자 문제를 "수익인식 기준을 원문에서 찾지 못하는 불편"으로 다시 정리했습니다.

## 과제 조건과 달라진 점

과제는 "스키마와 검색·프롬프트 파이프라인을 바꾸지 말고, 검색 순서와 답변 프롬프트의 출처·거부 규칙은 그대로 두라"고 합니다. 결과 차이를 자료 차이로 읽기 위해서입니다. 아래는 그대로 둔 것과, 실험 근거를 갖고 바꾼 것입니다.

| 항목 | 상태 | 근거 |
|---|---|---|
| 벡터스토어 스키마 `{id, text, url, section, vector}` | **그대로** | 설정 기록은 별도 파일(`ifrs-docs.meta.json`)로 분리 |
| 검색 순서 (벡터 top-10 + BM25 top-5) | **그대로** | 코드 위치만 `search-core.ts`로 옮김 (로직 동일, 앱·터미널 결과 일치 확인) |
| 근거 약함 기준 0.55와 보수 지시 문구 | **그대로** | 한 곳(`WEAK_THRESHOLD`)에서 정의하도록 정리만 함 |
| 거부 규칙 ("자료에 없으면 없다고 말한다") | **그대로** | 도메인 밖·다른 기준서·사례 판단 처리는 PRD에서 정한 대로 시스템 메시지에 **추가** |
| 임베딩 입력 형식 | **변경** | 실험 1 — 관련·무관 질문의 점수 간격 0.042 → 0.115 |
| 프롬프트 출처 표시 형식 | **변경** | 실험 3 — v1은 머리 베낌 3/5와 잘못된 거절, v3은 위험한 실패 0건 |
| 답변 `temperature` | **추가 (0)** | 실험 비교를 위해 같은 질문에 같은 답이 나오도록 |

바꾼 항목은 모두 한 번에 변수 하나만 바꾸고, 바꾸기 전 형식(v1 등)을 코드에 남겨 다시 비교할 수 있게 했습니다.

왜 원문 대신 요약을 썼는지는 [기준서 원문을 그대로 쓰지 않은 이유 (저작권)](#기준서-원문을-그대로-쓰지-않은-이유-저작권)에 자세히 적었습니다. 사내 가이드(`docs/revenue-guide.md`)는 이 프로젝트를 위해 직접 쓴 교육용 가상 문서입니다.

## 한계와 확장 방향
- **자료 범위**: 기준서 본문·적용지침 중 26개 문단 묶음만 요약했습니다. 라이선싱, 고객의 선택권, 재매입약정 등은 일부러 넣지 않았고(근거 부족 질문 실험용), 적용사례(IE)와 **금융감독원 질의회신·실무 해석 사례는 넣지 않았습니다.** 실무 질문에 강한 도구가 되려면 이런 자료를 이용 조건을 확인한 뒤 추가해야 합니다.
- **모델 크기**: 로컬 2B 모델이라 여러 청크를 잇는 답과 자료에 없는 주제의 거절이 약합니다(고정 질문 실험의 라이선스 환각, "5단계" 질문의 불완전한 답). 같은 구조에서 Gemini 엔진을 고르면 더 큰 모델로 비교해 볼 수 있습니다.
- **5단계 뼈대 고정**: 5단계 개요를 시스템 메시지에 고정해 두면 "5단계가 뭐야?" 같은 질문이 나아질 수 있습니다. 다음 실험 후보로 남겨 두었습니다.

- `docs/revenue-guide.md` — 교육용 사내 가이드 (청크 IFRS-015~018의 원문)
- `data/chunks.json` — 청크 원본 (벡터 없음)
- `app/public/ifrs-docs.json` — 벡터스토어 (`{id, text, url, section, vector[768]}`)
- `app/public/ifrs-docs.meta.json` — 벡터스토어를 만든 임베딩 설정 (안전장치)
- `app/src/embed-format.ts` — 임베딩 계약: 모델, 입력 형식 (브라우저·Node 공용)
- `app/src/search-core.ts` — 검색 계약: 하이브리드 순위 계산, 약한 근거 기준 `WEAK_THRESHOLD` (브라우저·Node 공용)
- `app/scripts/node-embedder.mjs` — Node 임베딩 파이프라인 (`embedDocument`, `embedQuery`)
- `app/scripts/embed-docs.mjs` — 청크 검사 → 벡터스토어 + 메타 생성 (`npm run embed`)
- `app/scripts/search.mjs` — 터미널 검색기 (`npm run search`)
- `app/src/prompt.ts` — 생성 계약: 시스템 메시지, 프롬프트 조립(형식 v1·v2·v3, 기본 v3), 인용 ID 확인 (브라우저·Node 공용)
- `app/scripts/ask.mjs` — 터미널 질문기 (`npm run ask`)
- `app/scripts/run-questions.mjs` — 실험용 일괄 실행 → `experiments/*.json`
- `data/fixed-questions.json`, `data/exp3-questions.json` — 고정 질문 세트
- `experiments/` — 실험 원문 답변과 측정값 (실패한 답도 지우지 않음)
- `app/src/rag.ts` — 브라우저 질문 임베딩, 검색 호출
- `app/src/ollama.ts` / `gemini.ts` — 답변 스트리밍, 판정 호출
- `app/src/judge.ts` — LLM-as-a-Judge 루브릭(근거 충실성·환각 통제·출처 표시) + refusal
- `.github/workflows/deploy.yml` — main에 push하면 `app/dist`를 GitHub Pages로 배포
